# テスト駆動開発

このプロジェクトはテスト駆動開発で進める。手順は `/implement` に、原則はここに書く。

## サイクル

**Red → Green → Refactor** を小さく回す。

1. **Red** — 失敗するテストを1つ書く
2. **失敗を確認する** — 実装を書く前に必ずテストを走らせ、期待した理由で失敗することを見る
3. **Green** — 最速でテストを通す。この段階では汚くてよい
4. **Refactor** — テストが緑のまま設計を整える

## 実装の3つの進め方

Green にする手段は状況で選ぶ。

| 手段 | いつ使うか |
|---|---|
| **仮実装** | 期待値をベタ書きして通す。まず1本通したいとき |
| **三角測量** | 仮実装が「たまたま通った」だけかもしれないとき、テストケースを増やして一般化を導く |
| **明白な実装** | 実装が自明なとき、頭の中のものをそのまま書く |

迷ったら仮実装から入る。三角測量は、正しい一般化が自分でも見えていないときの道具。

## テストを書く前に TODO リストを作る

実装に入る前に、テスト観点のリストを書き出す。
リストがあることで「次に何を書くか」で迷わなくなり、どこまで進んだかが見える。

リストは会話の中でもよいが、Phase 単位のものは `docs/plan.md` のチェックリストに反映する。

## 守ること

- **失敗を見ていないテストは信じない。** 常に緑のテストは、何も検証していない可能性がある
- **1つのテストで1つのことだけ検証する。** 落ちたときに原因が一意に決まる
- **テスト名は仕様を表す日本語で書く。** 日本語で書くのは、家系図のドメイン用語
  （続柄・養子縁組・家族ユニット）を英語に訳すと意味が失われるため
  - 良い例: `再婚した人物の子は、婚姻ごとに別のグループとして配置される`
  - 悪い例: `test layout 2`
- **テストコードもプロダクトコード。** 重複や読みにくさは同じように直す
- **リファクタリングはテストが緑のときにだけ行う。** 赤いまま設計を変えない

## 層ごとの適用

| 層 | 検証の手段 |
|---|---|
| `src/domain/**` | **必ず TDD。** 純粋関数なのでテストが最も効く。例外なし |
| `worker/**` | **必ず TDD。** バリデーションと SQL の境界をテストで固める |
| `src/design-system/**` | Storybook のストーリーを先に書く。見た目は目で確認する |
| `src/features/**` `src/pages/**` | 手動確認でよい。ロジックが出てきたら `domain/` に移してテストする |

`design-system/` にテストを強制しない理由は、見た目の正しさを assert で表現しても
壊れやすいだけで、Storybook で目視するほうが確実なため。
ただし**ストーリーが書きにくいと感じたら、それは層の分離が崩れたサイン**。
ロジックが混ざっていないか疑う。
