# コードコメント

このプロジェクトは t-wada の HWWWn 原則に従う。

> コードには How、テストコードには What、コミットログには Why、コードコメントには Why not を書こう
> — [Takuto Wada](https://x.com/t_wada/status/904916106153828352)

| 場所 | 書くこと |
|---|---|
| コード | **How** — どう実現しているか。コード自体が語る |
| テストコード | **What** — 何が仕様か。テスト名が仕様書になる |
| コミットログ | **Why** — なぜこの変更を入れたか |
| コードコメント | **Why not** — なぜ他のやり方を採らなかったか |

## コードコメントに書くこと

コメントの第一の役割は、**読んだ人が「もっと素直に書けるのでは」と思って壊すのを防ぐ**こと。

書くべきなのは以下。

- 素直な実装を採らなかった理由
- 一見不要に見えるコードが必要な理由
- 意図的に対応していない範囲と、その理由
- 外部の仕様・制約に引きずられている箇所（ブラウザの挙動、D1 の制限 など）

```ts
// writing-mode: vertical-rl は使わない。SVG text ではブラウザ差が大きく、
// 行間と約物の制御が効かないため、文字単位で配置する。
```

```ts
// 養子リンクは世代制約に含めない。含めると実親経由と養親経由で矛盾する
// ケースが頻発し、ほとんどの家系で警告が出て使い物にならなくなる。
// → docs/adr/0002-generation-assignment.md
```

判断の背景が長くなる場合は ADR に書き、コメントからはリンクだけ張る。

## コードコメントに書かないこと

- **コードを読めば分かること。** `// カウンタをインクリメントする` のような説明
- **What の再掲。** 関数が何をするかは名前とテストが語る
- **変更履歴。** git が持っている
- **コメントアウトされたコード。** 消す。git から戻せる

## 例

```ts
// 悪い: コードが語っていることの再掲
// persons を id でマップに変換する
const byId = new Map(persons.map((p) => [p.id, p]));

// 良い: Why not
// Map に載せ替えてから引く。persons は50件程度だが、
// 世代割当のループが O(n^2) になるのを避けたい。
const byId = new Map(persons.map((p) => [p.id, p]));
```

```ts
// 悪い: 何をしているかの説明
// partner1_id と partner2_id をソートしない
const pair = [family.partner1Id, family.partner2Id];

// 良い: 壊されるのを防ぐ
// ID 昇順に正規化してはいけない。partner1/partner2 の順序は
// 家系図上の左右の配置を意味する。
const pair = [family.partner1Id, family.partner2Id];
```
