# 実装からマージまでを一気に進める

対象: $ARGUMENTS

**このスキルは既存のスキルを順に呼ぶだけ。** 各工程の手順はそれぞれのスキルが正で、
ここには書き写さない。書き写すと必ず片方だけ古くなる。

ここに書くのは**スキルとスキルの間**にある、どこにも書かれていないこと。
CI の待ち方、マージの仕方、その後のローカルの整え方、そしてどこで止まるか。

```
/implement → /commit → /pr → CI 待ち → マージ → ローカル整理
```

**1回の起動で `docs/plan.md` のタスク1つ分。** 複数タスクを進めたいなら繰り返し呼ぶ。
無人で何タスクもマージし続けない。レビューされない変更が積み上がる。

## 0. 起動時に確かめる

```bash
git branch --show-current
git status --short
gh pr list --state open
```

- **未コミットの変更が既にある** → `/implement` が手順0で現在地を割り出す。任せる
- **自分のブランチに open な PR がもうある** → 実装は済んでいる。手順4（CI 待ち）から
- **`main` にいる** → `/implement` が作業ブランチを切る

**このスキルを起動した時点で、マージまでの承認とみなす。** 工程ごとに確認を取り直さない。
ただし後述の「止まるとき」に当たったら、そこで手を止めて user に報告する。

## 1〜3. 実装・コミット・PR

`/implement` → `/commit` → `/pr` をそのまま呼ぶ。引数は渡さない
（このスキルに引数が渡されていれば `/implement` にだけ渡す）。

`/implement` は内部で `/simplify` と動作確認まで含んでいる。飛ばさない。
`/pr` が控えた動作確認の結果は、そのまま PR 本文に載る。

## 4. CI を待つ

```bash
gh pr checks --watch --fail-fast
```

`--watch` は全チェックが出揃うまでブロックし、`--fail-fast` は1つでも落ちた時点で抜ける。

**終了コードで分岐する。**

| 終了コード | 意味 | どうするか |
|---|---|---|
| 0 | 全て成功 | 手順5へ |
| 1 | どれかが失敗 | **止まる。** 落ちたジョブのログを読んで報告する |
| 8 | チェックが1件も無い | 下記「CI が無いとき」へ |

失敗したときは `gh run view --log-failed` でログまで読んでから報告する。
「CI が落ちました」だけでは user が結局自分で見に行くことになる。

### チェックがあることと、テストが回っていることは別

`gh pr checks` が緑でも、それが**何を検証したチェックなのか**を必ず見る。
シークレット検出やライセンス確認のような外部アプリのチェックは、
`pnpm test` を1行も走らせずに pass する。

```bash
gh pr checks --json name,bucket
```

このリポジトリの CI は `test` / `lint` / `typecheck` の3つのチェックを付ける
（`.github/workflows/ci.yml`）。**この3つが揃って緑であることを確かめる。**
名前を見て1つでも欠けていれば、それは「CI が緑」ではない。

### CI が無いとき

ワークフローが動かない、あるいはチェックが1つも付かないときに限る。
ローカルの `pnpm test` / `pnpm lint` / `pnpm typecheck` が緑であることを
マージの根拠にしてよいが、**そうしたことを user に明示する。**
黙って通すと、CI が守ってくれていると誤解したまま次の PR が積まれる。

3つ揃うはずのチェックが欠けているのは、設定が壊れているサインでもある。
ローカルで代替する前に、なぜ付かなかったかを一度見る。

## 5. マージする

```bash
gh pr merge --merge --delete-branch
```

`--merge`（マージコミット）で揃える。squash は使わない。
このプロジェクトはコミットログの Why が資産で、squash すると
「なぜそうしたか」が1つに潰れて失われる。

## 6. ローカルを整える

```bash
git switch main
git pull --ff-only
git fetch --prune
```

- `gh pr merge --delete-branch` は**リモートとローカルの両方**のブランチを消し、
  main に切り替えるところまでやる。それでも上の3行は流す。
  gh がどこまでやったかは状況で変わる
- `--prune` を忘れると、消えたリモートブランチの remote-tracking ref が残り、
  次に `git branch -a` を見たときに「まだあるのか」と迷う
- `git pull` は `--ff-only` を付ける。付けないと、うっかりマージコミットが生える

最後に `pnpm test` を流し、**マージ後の main が緑であること**を確認する。
PR が緑でも、その間に入った別の変更と組み合わさって落ちることはある。

## 7. 止まるとき

以下に当たったら、そこで止めて user に報告する。**回避して先に進まない。**

| 状況 | なぜ止まるか |
|---|---|
| テストが赤いまま Green にできない | `/implement` の責務。ここで握り潰さない |
| CI が失敗した | 落ちた理由が分かるまでマージしない |
| テストを回す CI が1つも無い | ローカル検証で代替してよいが、**その判断を user に見せてから**進む |
| main とコンフリクトしている | 解決方針は user のもの。勝手に片方を捨てない |
| PR にレビューコメントが付いている | 未対応のまま閉じない |
| 設計ドキュメントと違う実装をしそうになった | `/implement` の手順1に戻る |

## このスキルが守らせたいこと

- **工程を飛ばさない。** 一気に進めることと、雑に進めることは違う。
  `/implement` が持っている「Red の確認」「`/simplify`」「動作確認」は
  速さのために削ってよい部分ではない
- **緑の意味を確かめてからマージする。** チェックマークが付いていることと、
  検証されたことは別
- **1回の起動で1タスク。** 誰も見ていない変更を積み上げない
- **止まるべきところで止まる。** 自動化の価値は、通る道を速く通ることであって、
  通ってはいけない道を通ることではない
