# 実装タスクを進める

対象: $ARGUMENTS

**引数は省略できる。** 省略された場合は現在地をリポジトリから割り出し、
続きから再開する。会話の履歴には頼らない。コンテキストを消してから
何度でも呼べる状態を保つのがこのスキルの前提。

フェーズは飛ばさない。Phase N のタスクが残っているうちは Phase N+1 に進まない。

## 0. 現在地を割り出す

**会話の履歴を前提にしない。** 以下を実際に実行して状態を読む。

```bash
git branch --show-current
git status --short
git log --oneline -10
pnpm test 2>&1 | tail -5     # 存在すれば
```

`docs/plan.md` を読み、チェックの付いていない最初のタスクとその Phase を確認する。

### 読み取った状態から、次にやることを決める

| 状態 | 再開する場所 |
|---|---|
| 未コミットの変更があり、テストが**赤** | TDD サイクルの途中。手順3の Green から |
| 未コミットの変更があり、テストが**緑** | 手順4（完了確認）から。**まだコミットしていない前提で進む** |
| 未コミットの変更が無く、plan.md に未完了タスクがある | 手順1から。そのタスクが対象 |
| 作業ブランチにいて、Phase の全タスクが完了 | 手順8。`/pr` を作るか user に確認する |
| `main` にいて、未完了タスクがある | 作業ブランチを切る（例: `git switch -c phase1/generation-assignment`） |

赤いテストが1本だけあり、それが未コミットなら、**それは書きかけの Red**。
消さずに Green にする。何を検証しようとしていたテストなのかは、
テスト名（日本語で仕様が書いてある）から読み取れる。

### 冒頭に必ず書くこと

**この応答の冒頭に、以下を明示する。** 何が起きているか user が見て分かる状態にする。

- 割り出した現在地（ブランチ、未コミットの有無、テストの赤緑）
- 対象タスクとその Phase
- 手順のどこから再開するか

対象が曖昧、あるいは1回の作業として大きすぎると判断したら、
実装に入る前に分割案を提示して user に確認する。

引数が渡されている場合は、それを対象の指定として優先する。
ただし現在地の読み取り自体は省略しない。未コミットの変更を
取りこぼしたまま別のタスクに進むと、関係ない変更が混ざる。

## 1. 設計ドキュメントを読む — 省略しない

対象タスクに対応する design ドキュメントを**実装を書く前に必ず読む**。

| 対象 | 読むもの |
|---|---|
| `src/domain/layout-engine/`, `src/domain/kinship/` | [docs/design/layout-engine.md](../../../docs/design/layout-engine.md) |
| `src/domain/models/`, `migrations/`, `worker/` | [docs/design/data-model.md](../../../docs/design/data-model.md) |
| `src/design-system/` | [docs/design/design-system.md](../../../docs/design/design-system.md) |
| 命名で迷ったとき | [docs/design/glossary.md](../../../docs/design/glossary.md) |
| 「なぜこの設計？」と思ったとき | [docs/adr/](../../../docs/adr/README.md) |

**設計ドキュメントとコードが食い違う実装をしそうになったら、そこで止まる。**
勝手にドキュメントと違う実装をしない。次のどちらかを選ぶ。

- ドキュメントが正しい → 実装をドキュメントに合わせる
- 実装しようとしている方が正しい → **先にドキュメントを直す。** そのうえで実装する。
  複数の選択肢を比べた結果なら `/adr` で判断を記録する

ドキュメントの修正と実装は別のコミットに分ける。

## 2. TODO リストを作る

実装に入る前に、テスト観点のリストを書き出して user に見せる。
これが無いと「次に何を書くか」で迷い、テストの粒度がぶれる。

`docs/design/layout-engine.md` の「テスト観点」のように、
設計ドキュメントに観点が書いてある場合はそれを起点にする。

## 3. Red → Green → Refactor

TODO リストの項目を1つずつ、以下のサイクルで潰す。原則は `.claude/rules/tdd.md`。

1. **Red** — 失敗するテストを1つ書く。テスト名は仕様を表す日本語
2. **失敗を確認する** — `pnpm test` を実行し、**期待した理由で**落ちることを見る。
   ここを飛ばさない。落ちるところを見ていないテストは何も検証していない可能性がある
3. **Green** — 最速で通す。仮実装 / 三角測量 / 明白な実装 から選ぶ。汚くてよい
4. **Refactor** — テストが緑のまま設計を整える。テストコードも同じように整える

層ごとの適用は `.claude/rules/tdd.md` の表に従う。
`src/domain/**` と `worker/**` は例外なく TDD。
`src/design-system/**` は Storybook のストーリーが Red の代わりになる。

### 途中で気づいたことの扱い

- **仕様の抜けに気づいた** → TODO リストに足す。その場で実装に飛ばない
- **設計判断が必要になった** → 1 に戻る。ドキュメントを直してから進む
- **今のタスクと関係ない問題を見つけた** → メモして user に伝える。今のコミットに混ぜない

## 4. 完了を確認する

以下が全て通ってからコミットに進む。

```bash
pnpm test        # 全テストが緑
pnpm lint        # 層境界ルールを含む。無効化して回避しない
pnpm typecheck   # 型エラーなし
```

lint が層境界で落ちたら、それは設計が間違っているというシグナル。
`eslint-disable` で黙らせず、`.claude/rules/layer-boundaries.md` の「詰まったときの対処」を見る。

（Phase 0 が終わるまでこれらのスクリプトは存在しない。その場合は該当分を飛ばす）

## 5. `/simplify` を動かす — コミットの前

**緑になった直後のコードをそのままコミットしない。** `/simplify` を動かし、
出てきた指摘を反映してからコミットする。

Green は「動く」ところまでしか保証しない。TDD の Refactor は自分で気づいた分しか
直せず、書いた直後は自分の書き方が一番読みやすく見える。
`/simplify` は別の視点（再利用・単純化・効率・抽象度）から見直すためのもの。

- 指摘は**全部そのまま入れない**。振る舞いを変えるもの、今のタスクの外に出るものは
  見送る。見送った理由は user に伝える
- 反映した内容が独立した関心事なら、**別のコミットに分ける**。
  「実装」と「整理」を1コミットに混ぜない
- 反映後に 4 をもう一度通す。整理してテストが落ちたら、それは整理ではない

「後で綺麗にする」は来ない。ここで整えたものだけがコミットされる。

## 6. 動作確認をする

テストが緑であることと、**実際に動くこと**は別。コミットの前に手で動かす。

| 変更の種類 | 確認の仕方 |
|---|---|
| 画面に出るもの | `pnpm dev` / `pnpm storybook` を起動し、ブラウザで実際に見て触る |
| `worker/**` の API | `curl` で叩き、レスポンスを見る |
| `src/domain/**` のロジック | テストが動作確認そのもの。境界値を1つ手で流して出力を見る |
| 設定・ビルド周り | `pnpm build` が通ること、生成物が期待の場所に出ること |

**確認したことは記録する。** 実行したコマンド、期待した結果、実際の結果を
控えておく。8 の PR 本文にそのまま使う。

見た目は**その場で目で見て確かめる**。PR にスクリーンショットは載せない
（GitHub が CLI から画像を貼る手段を用意していないため）。
崩れていたらここで直す。文章で「崩れていない」と書いて済ませない。

「テストが緑だから動くはず」で飛ばさない。設定ファイルの1行が違うだけで
dev サーバーが起動しない、といった類はテストでは絶対に捕まらない。

## 7. 記録を残す

1. `docs/plan.md` の対象タスクにチェックを入れる
2. 設計判断をしたなら `/adr` で記録する
3. `/commit` でコミットする。**コミットログには Why を書く**

TODO リストに残りがあれば 3 に戻る。
Phase の全タスクが終わったら、`/pr` で PR を作るか user に確認する。
6 で控えた動作確認の結果を PR 本文に載せる。

### 中断するときに残すもの

コンテキストを消して再開できるかは、**リポジトリに何が残っているか**で決まる。
中断する前に、次のどちらかの状態にしておく。

- **コミット済み** — plan.md のチェックまで含めて手順7を終える
- **未コミットだが状態が読める** — 書きかけの Red が1本だけある、など

避けるべきなのは、複数のタスクの変更が未コミットで混ざった状態。
手順0がどこから再開すべきか判断できなくなる。

## このスキルが守らせたいこと

- **設計ドキュメントを読まずにコードを書かない。** ドキュメントが正で、コードが従う
- **失敗を見ていないテストを信じない**
- **整えてからコミットする。** 緑になった直後のコードをそのまま残さない
- **動かしていないものを「できた」と言わない。** テストが緑なのと動くのは別
- **今のタスクと関係ない変更を混ぜない。** 1コミット1関心事
- **判断したら記録する。** なぜそうしたかは、書かなければ必ず失われる
