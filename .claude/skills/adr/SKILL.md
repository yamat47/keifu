# 設計判断を記録する

決定: $ARGUMENTS

**引数は省略できる。** 省略された場合は、記録すべき判断を自分で探す。

```bash
git log main..HEAD --format='%h %s%n%b'   # 作業ブランチのコミットログ
git status --short
git diff main...HEAD --stat
```

コミットログの Why と未コミットの変更を読み、下の「書くべきか判断する」に
当てはまるものを探す。**候補を挙げて user に確認してから書く。**
勝手に1つ選んで書き始めない。ADR は後から書き換えない文書なので、
何を記録するかの選択自体が判断になる。

候補が見つからなければ「記録すべき判断は見当たらない」と言って終わる。
無理に絞り出さない。選択肢が実質1つしかなかった判断を書くとノイズになる。

## 書くべきか判断する

書く。

- 複数の選択肢を比較して1つを選んだ
- 一見不自然に見える実装を、理由があって採用した
- 「素直にやるとこうなるが、それでは駄目な理由がある」
- 後から誰か（未来の自分を含む）が元に戻したくなりそう

書かない。

- 選択肢が実質1つしかなかった
- コミットログの Why で十分に収まる粒度
- 実装の詳細であって設計ではない

**迷ったら書く方に倒す。** 読まれない ADR のコストより、
「なぜこうなっているのか誰も分からない」コードのコストの方が大きい。

## 手順

1. `ls docs/adr/` で次の番号を確認する（連番、4桁ゼロ埋め）
2. `docs/adr/NNNN-english-slug.md` を作る。スラッグは英語のケバブケース
3. 下のテンプレートを埋める
4. `docs/adr/README.md` の一覧表に行を追加する
5. `/commit` でコミットする。**実装とは別のコミットにする**

## テンプレート

```markdown
# ADR-NNNN: <決定を一文で>

- Status: Accepted
- Date: YYYY-MM-DD

## 状況

<何を決めようとしているのか。どんな制約があるのか>
<当初考えていた案があればそれも書く>

## 決定

<何を決めたか。簡潔に>
<詳細な仕様は docs/design/ に書き、ここからはリンクする>

## 理由

<なぜその決定に至ったか>
<「なぜ素朴な方法では駄目なのか」を具体的に書く。ここが ADR の本体>

## 採用しなかった案

**<案の名前>**
<なぜ採らなかったか>

## 影響

<この決定によって何が変わるか>
<他のドキュメント、UI の操作、スキーマへの波及>
```

## 書き方の注意

- **「理由」に一番紙面を使う。** 決定そのものは design ドキュメントにも書いてある。
  ADR にしか無いのは、そこに至った理由と捨てた選択肢
- **具体的に書く。** 「保守性が高いため」ではなく
  「(親, 子) ペアだと父の行と母の行で sibling_order が分散し、不整合が入るため」
- **採用しなかった案を必ず書く。** これが無いと、後から同じ案を検討し直すことになる
- **一度 Accepted にした ADR は書き換えない。** 判断が変わったら新しい ADR を書き、
  古い方の Status を `Superseded by ADR-NNNN` に変える。判断の変遷自体が記録になる
- 用語は `docs/design/glossary.md` に揃える
