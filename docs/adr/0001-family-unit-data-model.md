# ADR-0001: 親子関係を家族ユニット経由で表現する

- Status: Accepted
- Date: 2026-07-26

## 状況

家系図の親子関係をどう永続化するか。
養子縁組・再婚・片親のみ判明、の3つを同時に満たす必要がある。

最初の案は `parent_child(parent_id, child_id, relation_type, marriage_id)` という
(親, 子) のペアを直接持つテーブルだった。

## 決定

親子関係を **家族ユニット (`families`)** を介して表現する。
子は `family_children` で family に属し、親は family の `partner1_id` / `partner2_id` から決まる。

再婚順序は family に1つではなく、`partner1_order` / `partner2_order` として
**partner ごとに2つ**持つ。

兄弟順 `sibling_order` は `persons` ではなく `family_children` に持つ。

詳細は [data-model.md](../design/data-model.md)。

## 理由

(親, 子) ペア案には、実装すると必ず詰まる問題が3つあった。

**1. 父母で行が二重化する**
1人の子に対して父の行と母の行ができ、`marriage_id` と `sibling_order` が
2箇所に分散する。「実父の行だけ削除された」ような半端な状態も作れてしまう。
family なら1行で父母が確定する。

**2. 再婚順序が誰にとっての順序か決まらない**
`marriages` に `marriage_order` を1つ持つと、
「A にとって2度目の婚姻だが、相手 B にとっては初婚」が表現できない。
これは特殊なケースではなく普通に起きる。

**3. 兄弟順の置き場所がない**
兄弟順は「その親グループの中での順序」であって人物のグローバル属性ではない。
養子は実親グループと養親グループの両方に属するため、
`persons.sort_order` に1つ持つと必ず破綻する。

family モデルはこの3つを構造的に解消する。
さらに、再婚の子のグルーピングが「family = 婚姻」であることから自動的に決まり、
`marriage_id` のような明示的な紐づけが不要になる。

GEDCOM の FAM レコードが同じ構造を採っており、
家系データを扱う上での定番であることも判断を後押しした。

## 採用しなかった案

**(親, 子) ペア + 制約を足して補強する**
上の3つを制約で防ぐことは原理的には可能だが、
「父の行と母の行の `sibling_order` が一致していること」のような制約は
SQL で表現できずアプリ側の検証に頼ることになる。構造で防げるものを検証で防ぐのは筋が悪い。

**GEDCOM 形式をそのまま採用する**
互換性は得られるが、仕様が大きく、今回必要なのはその一部にすぎない。
考え方だけ借りて、スキーマは要件に絞った。

## 影響

- 「親を追加する」という UI 操作は、裏で family を作る操作になる。
  片親のみ判明している場合も family を1つ作る必要がある
- 用語を「婚姻 (marriage)」から「家族ユニット (family)」に変えた。
  [glossary.md](../design/glossary.md) を参照
- 子は必ずどこかの family に属する。family に属さない人物は最上位世代のみ
