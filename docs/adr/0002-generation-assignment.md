# ADR-0002: 世代割当を差分制約系として解く

- Status: Accepted（解法を 2026-07-26 に補足）
- Date: 2026-07-26

## 状況

家系図は世代ごとに段を分けて上から下へ配置する。
そのためには各人物に世代番号を割り当てる必要がある。

素朴には「ルートから深さ優先で辿って深さを世代にする」で済みそうに見えるが、
養子縁組と再婚があると成立しない。

- 同一人物が実親経由で3代目、養親経由で4代目になる
- 配偶者どうしの世代が血縁計算では一致しない
- 連結していない家系（分家など）が複数ある
- 叔父と姪の婚姻のように、そもそも制約が矛盾するケースが戸籍には実在する

## 決定

世代割当を**差分制約系**として定式化し、有向グラフの最長路 / Bellman-Ford で解く。

- 変数 = 各人物の世代 `g(p)`
- 制約A: 血縁の親子について `g(child) = g(parent) + 1`
- 制約B: 同一 family の partner 同士について `g(a) = g(b)`
- **養子リンクは制約に含めない**
- 連結成分ごとに最小世代を 0 に正規化する

矛盾は**負閉路**として検出する。
検出したら例外を投げず、矛盾した婚姻制約（制約B）を落として計算を続け、
`diagnostics` に警告を積む。

## 理由

**なぜ深さ優先探索ではないか**
グラフが木ではなく DAG なので「深さ」が一意に決まらない。
どの経路を辿ったかで結果が変わる = 出力が非決定的になる。

**なぜ制約充足として書くか**
「親子は1つ差」「配偶者は同じ」という2種類の要求を、
アルゴリズムの副作用ではなく明示的な制約として書ける。
仕様がそのままコードに現れるので、テストで検証しやすい。

**なぜ矛盾を検出できることが重要か**
手入力である以上、誤登録は必ず起きる。
負閉路検出は「データが間違っている」ことをアルゴリズムが自力で気づける唯一の仕組みで、
これが無いと不正なデータが無言で妙なレイアウトになって現れる。

**なぜ矛盾時に例外を投げないか**
家系図全体が描画できなくなるより、一部の配偶者の高さがずれても
全体が見えるほうが編集作業を進められる。
警告を出して `generation_override` による手動解決を促す。

**なぜ養子リンクを制約に含めないか**
含めると、実親経由と養親経由で世代が矛盾するケースが頻発し、
ほとんどの家系で警告が出て使い物にならなくなる。
養子縁組は血のつながりによる世代を変えるものではない、と割り切った。
養子リンクは描画時の補助線として扱う。

## 採用しなかった案

**世代を DB に持たせて手入力させる**
入力コストが高く、人物を1人足すたびに周囲の世代を人間が調整することになる。
自動計算 + 例外時のみ `generation_override` で上書き、という形に落ち着かせた。

**汎用のグラフレイアウトライブラリに任せる**
d3-hierarchy などは木を前提としており、この DAG が乗らない。
また「配偶者が隣接している」「兄弟が連続している」という家系図固有の要求を表現できない。

## 補足: 解法は Bellman-Ford ではない

実装してみると、上に挙げた制約は**全て等式**だった。
不等式が1つも無いので、連結成分の中では1人決まれば全員決まる。
制約を1つずつ課し、両端が別成分なら片方を丸ごと平行移動して併合すれば解ける。

矛盾も負閉路を探すまでもなく、「両端が同じ成分に居るのに、その制約が要求する差が
満たされていない」として、その制約を課す瞬間に分かる。

最長路 / Bellman-Ford は不等式制約のための機械であり、ここでは併合1回に潰れる仕事を
反復で解くことになる。定式化（差分制約系として書く）という決定は変えず、
解法だけを差し替えた。詳細は [layout-engine.md](../design/layout-engine.md)。

## 影響

- `persons` に `generation_override` カラムが必要
- レイアウトエンジンの出力に `diagnostics` フィールドが必要
- UI 側は警告を表示する手段を持つ必要がある
- 横位置計算は別の問題として扱う（主系統を1つ選んで木にする）。
  [layout-engine.md](../design/layout-engine.md) を参照
