# ADR-0006: レイアウト計算はグラフ検証を呼ばない

- Status: Accepted
- Date: 2026-07-26

## 状況

Phase 1 の最後で、5つの工程を繋ぐ入口 `computeLayout` を作った。
ここでグラフ検証（自己親子・祖先ループ・参照整合性）を呼ぶかどうかを決める必要がある。

[data-model.md](../design/data-model.md) には
「**API 層とレイアウトエンジンの両方から同じ関数を呼ぶ**」と書いてあった。
一方で Phase 1 で実装した工程は、どれも docstring に
「参照整合性は前提とする」と書いて検証を呼んでいない。
**ドキュメントと実装が食い違ったまま Phase 2 に入ろうとしていた。**

## 決定

**`computeLayout` は `validateGenealogyGraph` を呼ばない。**
検証済みの家系を受け取る前提で書き、呼び出し側が描画の前段で検証する。

data-model.md の一文は「書き込み API と描画の前段の両方から同じ関数を呼ぶ」に直す。
共有すべきは**実装が1つであること**であって、レイアウトエンジンが呼ぶことではない。

## 理由

検証と計算では、失敗したときに取るべき振る舞いが違う。

グラフ検証の違反（`GraphViolation`）は**登録を拒否する**ためのもので、
1件でもあれば家系図を描かない。レイアウト計算の診断（`diagnostics`）は
**描き切ったうえで警告する**もので、叔父と姪の婚姻のように戸籍では実在する。
1つの関数が両方を返すと、呼び出し側は返ってきたものを見て
「これは描いてよいのか」を毎回判断することになる。

置き場所としても、検証が要るのは**データが変わる瞬間**（登録・更新・インポート）であって、
描画のたびではない。50人規模なら祖先ループの検出は一瞬で終わるが、
毎描画で走らせても新しい違反は出てこない。同じ答えを何度も計算することになる。

## 採用しなかった案

**`computeLayout` の中で検証し、違反があれば例外を投げる**

呼び出し側が検証を忘れられなくなる点は魅力的だった。
採らなかったのは、Phase 4 の編集画面が「入力途中の壊れた家系」をプレビューする
可能性があるため。編集中に一時的に参照が切れるたびに図が消えるより、
警告を出しながら描けるところまで描くほうが編集作業を進められる。
これは世代の矛盾を `diagnostics` で扱うのと同じ判断
→ [ADR-0002](0002-generation-assignment.md)

**`validateGenealogyGraph` が `ValidatedGenealogy`（branded type）を返し、
`computeLayout` がそれだけを受ける**

前提を型に載せられるので、散文で「検証済みの家系を渡すこと」と書くより強い。
今の時点で採らなかったのは、検証を通る経路がまだ1つも無いため
（Phase 2 は fixtures を直読みする）。型を先に入れると、
fixtures を描くだけのコードが「検証を通したことにする」キャストを書くことになり、
型で守っているつもりで穴を1つ開けることになる。

Phase 3 で API 経由の読み込みが入ったときに再検討する。

## 影響

- 検証を通っていない家系を `computeLayout` に渡すと、収録されていない人物を
  指す線は黙って落ちる。壊れた図が出るだけで、例外にはならない
- 呼び出し側で検証を強制する仕組みは無い。
  [plan.md](../plan.md) の Phase 2・Phase 3 に、読み込み経路で検証を通す項目を置く
- レイアウトエンジンの公開面は `computeLayout` だけに絞ってある
  （`src/domain/layout-engine/index.ts`）。工程ごとの関数を外から呼べないので、
  検証を飛ばした状態で途中の工程だけを使うこともできない
