# レイアウトエンジン

家系図の座標計算の**正**。実装は `src/domain/layout-engine/`。

用語は [glossary.md](glossary.md)、入力データの形は [data-model.md](data-model.md) を参照。
世代割当の定式化に至った経緯は [ADR-0002](../adr/0002-generation-assignment.md)。

## 責務

**純粋関数**である。JSX・DOM・スタイル・I/O を一切含まない。

```
入力: { persons[], families[], familyChildren[] }
  ↓ 1. 世代割当
  ↓ 2. 主系統の抽出
  ↓ 3. 横位置計算
  ↓ 4. 結線パス生成
  ↓ 5. 座標変換（向きの適用）
出力: { nodes: [{ personId, x, y }], links: [{ kind, path }], diagnostics[] }
```

同じ入力からは常に同じ出力が出ること。乱数・現在時刻・ID の生成順に依存しない。

## 1. 世代割当 — 差分制約系として解く

養子と再婚があると、世代は素朴には決まらない。
同一人物が実親経由で3代目、養親経由で4代目になるケースが実在する。

以下の制約充足問題として解く。

- 変数 = 各人物の世代 `g(p)`
- 制約A: 血縁の親子について `g(child) = g(parent) + 1`
- 制約B: 同一 family の partner 同士について `g(a) = g(b)`
- **養子リンクは制約に含めない**
- どの制約にも現れない人物は、単独の連結成分として世代 0 になる
- 連結成分ごとに、最小世代が 0 になるよう正規化する

**制約が全て等式なので、連結成分の中では1人決まれば全員決まる。**
制約を1つずつ課し、両端が別の成分なら片方の成分を丸ごと平行移動して併合する。
50人規模では計算コストは無視できる。

不等式が無い以上、最長路 / Bellman-Ford は使わない。あれは不等式制約のための機械で、
ここでは併合1回に潰れる仕事を反復で解くことになる。

### `generation_override` は正規化のあとに上書きする

`persons.generation_override` が設定されていれば、**正規化まで終えた世代をその値で上書きする。**
制約系を解く前に固定するのではない。子や配偶者には伝播しない。

**理由**: 制約として先に固定すると、そのあとの正規化が連結成分ごと平行移動させるため、
ユーザーが入力した値と最終的な世代がずれる。手動指定は矛盾を目で見て直すための逃げ道であり、
入力した数字がそのまま段になることが最優先になる。

伝播させないのは、伝播先で新たな矛盾を生むため。1人ずらしたいだけの操作で
警告が増えるより、ずらしたい人物を個別に指定してもらうほうが結果が読める。

### 矛盾の扱い

矛盾は、**既に決まっている差と食い違う制約**として検出できる。
両端が同じ連結成分に居るのに、その制約が要求する差が満たされていない状態を指す。
叔父と姪の婚姻のように、戸籍では実在しうるケースで発生する。

矛盾を検出したら例外を投げずに `diagnostics` に警告として積み、
矛盾した制約のうち婚姻制約（制約B）を落として計算を続ける。
UI 側は警告を表示し、`generation_override` による手動解決を促す。

**理由**: 家系図全体が描画できなくなるより、一部の配偶者の高さがずれても
全体が見えるほうが編集作業を進められる。

血縁制約（制約A）どうしが矛盾することもある。複数の実親 family に属する人物で、
実親どうしの世代が揃っていない場合に起きる。この場合は**後から課した制約A**を落とす。
制約Aは1つも落とさずに済ませたいが、どちらか一方しか採れない以上、
入力順という説明可能な基準で選ぶ。どちらを採るかは `generation_override` で覆せる。

### 養子リンクを制約に含めない理由

含めると、実親経由と養親経由で世代が矛盾するケースが頻発し、
ほとんどの家系で警告が出て使い物にならなくなる。
養子縁組は「血のつながりによる世代」を変えるものではない、と割り切る。

## 2. 主系統の抽出

養子や複数親の存在により、家系グラフは**木ではなく DAG** になる。
そのままでは木のレイアウトアルゴリズムを適用できない。

各人物について、所属する family のうち1つを **主系統 (primary family)** として選ぶ。

1. `biological` で属する family を優先する
2. 複数あれば `family_id` が最小のものを選ぶ
3. どの family にも属さない人物（最上位世代）は主系統を持たない

主系統だけを残すとグラフは森（複数の木）になる。これを木として配置する。

## 3. 横位置計算

主系統の森に対して Reingold-Tilford 風に、部分木の幅を積み上げて配置する。
出力は `personId → siblingAxis`。1人が1スロットを占め、隣り合う人物の差が 1 になる。

- **夫婦は1ユニット**として隣接配置する。`partner1` が左、`partner2` が右
- **兄弟は `siblingOrder` 順**に連続配置する
- 再婚がある場合、配偶者を婚姻順（`partnerNOrder`）に並べ、
  それぞれの family の下に子をぶら下げる
- 連結していない複数のルートは、横に並べて配置する

汎用のクロス最小化（Sugiyama 法など）を使わない理由は、
50人規模では「夫婦が隣接し、兄弟が連続している」ほうが交差数の少なさより読みやすいため。

### 配置の単位は「配偶ブロック」

木の節は人物ではなく、**1人のホストとその配偶者たち**をまとめた配偶ブロックにする。
ブロックの下には、ホストの family ごとの子がぶら下がる。

**ホストは主系統を持つ側**。主系統を持つ人物は親の下に置かれる位置が既に決まっており、
配偶者はそこに寄せるしかない。逆に主系統を持たない人物（婚入した配偶者）は
自分を置く場所を持たないので、ホストの隣に付く。

配偶者を付ける向きは、ホストが `partner1` なら右、`partner2` なら左。
こうすると単婚の場合に「`partner1` が左」が自然に満たされる。
複数の配偶者はホストの `partnerNOrder` 順に、その向きへ積む。

どちらの partner も主系統を持たない family では、婚姻順の早い側をホストにしてルートにする。
並んだときは `partner1` をホストにする。どちらがホストでも左右の並びは変わらず、
差が出るのはルートどうしの並び順だけなので、基準が1つに決まっていればよい。

### 両方が主系統を持つ夫婦は隣接させない

叔父と姪の婚姻のように、夫婦の双方が主系統を持つことがある。
このとき**どちらも動かさず、隣接を諦める**。婚姻線は離れた2点を結ぶ。

片方をもう片方の隣に移すと、その人物は自分の兄弟列から抜ける。
兄弟の連続はこの家系図で最も読み取りやすさに効く性質であり、
夫婦の隣接1件のためにそれを崩す取引は割に合わない。
そもそも世代が食い違っている（→ 婚姻制約の矛盾）ため、
隣に置いても同じ段には並ばず、隣接させた見返り自体が小さい。

同じ理由で、**既にどこかの配偶者として置かれた人物は、別の family のホストにならない**。
2度婚姻した婚入者は、最初の婚姻（`partnerNOrder` 昇順、同順なら `familyId` 昇順）でだけ隣接する。

### 部分木は重ならない帯を占める

ブロックの幅は `max(自身の行に並ぶ人数, 子ブロックの幅の合計)`。
子ブロックを左から順に敷き詰め、幅の余った側にブロック自身を中央寄せする。

部分木どうしが帯を共有しないので、輪郭を突き合わせる本来の Reingold-Tilford より
横に広がる。50人規模では紙面の余りより「どの部分木がどこまでか」が
目で追えることを採る。

ルートの並び順はホストの `personId` 昇順。連結していない家系のあいだに
意味のある順序は無く、入力順に依存しない基準が要る。

## 4. 結線パス生成

| 線種 | 対象 | 表現 |
|---|---|---|
| 婚姻線 | family の partner 間 | 平行な2本の path（二重線）。SVG に `border: double` は無い |
| 実子線 | `biological` の親子 | 実線 |
| 養子線 | `adopted` の親子 | 点線 |
| 兄弟バー | 同一 family の子をまとめる横線 | 実線 |

主系統に含まれなかったエッジ（養子縁組、2つ目の親）は、
ノードの配置が確定した**後に**ベジェ曲線で結ぶ。

線の太さ・色・破線パターンは design-system 側のトークンで決める。
レイアウトエンジンは「どの種類の線を、どの座標に引くか」だけを返す。

## 5. 座標変換 — 向きの抽象化

レイアウトエンジンの内部計算は `(generationAxis, siblingAxis)` の抽象座標で行い、
最後に **orientation adapter** で画面座標 `(x, y)` に変換する。

現在の実装は「上→下」のみ:

```
x = siblingAxis * SIBLING_PITCH
y = generationAxis * GENERATION_PITCH
```

この分離により、将来「右→左（伝統的な巻物形式）」を
adapter の差し替えだけで追加できる。レイアウト本体は変更不要。

## テスト観点

`src/fixtures/` のサンプル家系を使い、以下を必ずカバーする。
UI を作る前にここを全部通す。

| # | ケース | 検証すること |
|---|---|---|
| 1 | 単純な3世代の直系 | 世代が 0,1,2 に割り当たる |
| 2 | 再婚（2つの family、それぞれに子） | 配偶者が婚姻順に並び、子が family ごとにグルーピングされる |
| 3 | 養子（実親 family と養親 family の両方に所属） | 実親からは実線、養親からは点線。世代は血縁側で決まる |
| 4 | 片親のみ（`partner2_id` が NULL） | 片側だけの family でも子が配置される |
| 5 | 連結していない複数ルート | それぞれが横に並び、重ならない |
| 6 | 世代制約の矛盾（叔父と姪の婚姻） | 例外を投げず `diagnostics` に警告が入る |
| 7 | 祖先ループ | 入力バリデーションで弾かれる |
| 8 | 決定性 | 同じ入力を2回渡すと完全に同じ出力になる |
| 9 | ノードの重なり | 全ノードの矩形が互いに交差しない |

テスト名は仕様を表す日本語で書く。例:
`再婚した人物の子は、婚姻ごとに別のグループとして配置される`
